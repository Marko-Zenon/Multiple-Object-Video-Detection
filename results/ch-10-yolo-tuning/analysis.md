# CH-10 — anchor-free tuning (YOLO11s): evidence and technical analysis

This is an evidence summary prepared for the students (Claude, CH-10 worker for Badabuba). Every number is read from tracked
files in `results/` and regenerated by `python results/ch-10-yolo-tuning/make_evidence.py` (byte-identical with `--tables-only`).
AP comes from the project evaluator (`movd/evaluate.py`): maxDets 500, the frozen ignore policy, curves on `val_fast` (714 frames),
headline numbers on all 2,846 `val_full` frames. This file states measurements and the mechanisms that can be checked in the code.
**The report's interpretation and conclusions are left to the students** (TODOs in section 12).

## 1. Protocol and runs

All runs use Ultralytics 8.4.207 and the COCO-pretrained `yolo11s.pt` (sha256 `85a76fe8…`). Each trains on the frozen
`train_rubric` split: 2,800 frames x 6 epochs = 16,800 images, batch 1 (`nbs` 64 accumulation), workers 0, AMP, seed 42,
flip-only augmentation, optimizer=auto (AdamW lr0 0.000833), with the masked ignore regions of the CH-02 policy.
The YOLO export was regenerated in this worktree and is byte-identical (5,600 files) to the CH-09/CH-11 export
(`export_check/identity.json`). The CH-09 checkpoint and predictions were re-verified against Marko's SHA-256 manifests
(163/163 and 145/145) before use.

| run | changed variable vs the CH-09 baseline | trained on | role |
|---|---|---|---|
| `yolo_baseline_marko_3050` | none (CH-09) | RTX 3050 6 GB (Marko) | reference baseline |
| `yolo_baseline_5070` | none: identical config re-run | RTX 5070 8 GB (Nazar) | replicate, measures run-to-run and GPU spread |
| `yolo_p2` | + P2 (stride 4) detection level, imgsz 1344 | RTX 5070 | variant (high-resolution head) |
| `yolo_imgsz1600` | imgsz 1344 -> **1600** (train and inference) | RTX 5070 | variant (higher input size; approved resolution exception) |

`yolo_imgsz1600` is the required higher-input-size variant. Changing the frozen 1344 long side was approved beforehand as a
CH-10 tuning exception. It costs (1600/1344)^2 = 1.42x the pixels per image, so it is a **resolution-sensitivity result, not
evidence at the fixed resolution**. The selection rule (`selection_rule.md`) was written before any variant finished training.

## 2. P2 decision (acceptance 4)

**Decision: P2 head run, after a passed compatibility smoke.** No loss or assignment fallback was needed.

- Model: `configs/models/yolo11s-p2.yaml`. Layers 0-22 are exactly yolo11s. An appended branch (layers 23-25) upsamples the
  P3 neck output and concatenates the backbone P2/4 feature. Detect reads `[P3, P4, P5, P2]`, giving strides `[8, 16, 32, 4]`.
  P3 is listed first so the Detect hidden widths equal the pretrained ones. Parameters: 9,569,360 vs 9,430,888 (+1.5%).
- Partial weight transfer (`p2_transfer.json`, `movd/yolo_p2.py`): the plain 8-class yolo11s is built exactly as the baseline
  trainer does, and all **499/499** of its tensors are copied (the Detect layer is renamed 23 -> 26). The **64 fresh tensors
  (139,986 elements)** are exactly the P2 branch. The COCO classification rows of person, bicycle, car, truck and bus are copied
  by class name, as in the baseline. Rows for van, tricycle and motor are random in both. Checks: the P3-P5 Detect inputs and
  outputs are bit-identical to the baseline start, and the parameters equal the trainer's own baseline start except those
  3 class rows (`tests/test_yolo_p2.py`, 7 tests).
- **A failed first smoke is kept** (`results/yolo_smoke_p2/README.md`). The first init built the plain model with placeholder class
  names, so Ultralytics' `load` skipped the by-name copy and all 8 class rows started untrained, although the log still said
  `Transferred 499/499`. The smoke caught it: val_fast mAP was 0.0103 vs 0.1223 for the 1600 smoke. That was diagnosed as a
  starting-weight difference, because neither smoke had taken a real optimizer step yet. After the fix, the smoke
  (`results/yolo_smoke_p2_fixed/`) scored 0.1178, and the full run started from that fixed init.
- Smoke checks (both variants, RTX 5070): 50 images x 2 epochs, stop after epoch 0, native resume with 255 optimizer entries,
  prediction and the project evaluator. Peak CUDA allocation at batch 1: 1.89 GB at imgsz 1600, 2.1 GB for P2.
  Both fit the 8 GB card at the baseline batch, so **no second parameter was changed**.

## 4. Run-to-run spread (the replicate)

The same configuration on another GPU moved val_full mAP by **0.0063** (0.1439 -> 0.1502) and the final val_fast mAP by
**0.0091**. Absolute differences on the other metrics: AP50 0.015, AP75 0.006, AP_S 0.008, AP_M 0.009, AP_L 0.001.
Per class the spread reaches 0.042 (bicycle) and 0.029 (tricycle). The two baseline curves also differ in shape: CH-09
peaks at epoch 2 (0.1845) and falls to 0.1441, while the replicate stays near flat (0.1609 -> 0.1532). Any variant difference
smaller than about 0.01 mAP (and any rare-class difference smaller than about 0.04) is within this one-pair spread.
The replicate also differs from CH-09 in GPU and CUDA kernels, so the spread combines nondeterminism and hardware.

## 5. Selection (rule fixed before the results)

`selection.json`: final-epoch val_fast mAP: baseline 0.1441, P2 0.1640, imgsz1600 **0.1751**. **Selected: `yolo_imgsz1600`.**
Its gain over the baseline (+0.031 on val_fast, +0.027 on val_full) is 3.4x the replicate spread on val_fast. Measured against
the replicate it is +0.022 / +0.021. The selected configuration uses the resolution exception (imgsz 1600), so its cost is reported
in section 9. Whether CH-14 may use 1600 is CH-12's decision.

The best run at the frozen 1344 is `yolo_p2` (rule 5): +0.020 val_fast over the CH-09 baseline, but only +0.011 over the
replicate, about the size of the spread (0.009). Its val_full gain (+0.019 / +0.012) is driven by AP_L and AP75 (section 6).

## 6. Small objects (acceptance 2)

COCO buckets (`size.csv`):

- **imgsz 1600** raises AP_M (+0.033) and AP_L (+0.019). AP_S changes by +0.003 vs the baseline and −0.006 vs the replicate,
  which is within the spread.
- **P2** raises AP_L (+0.057) and AP75 (+0.032). AP_S is lower: −0.008 vs the baseline and −0.016 vs the replicate.
  **The pre-registered hypothesis that a stride-4 level raises AP_small is not supported** after 6 epochs. This negative
  result is kept.

Finer buckets inside COCO "small" (`fine_size.csv`, `figures/fine_size.png`; supplementary, same GT, crowd handling and 500 cap.
The 32-96 px and >96 px rows equal AP_M / AP_L exactly, a built-in cross-check). val_full has **no** target under 8 px, 380 under
16 px, 7,376 at 16-24 px and 14,154 at 24-32 px.

| bucket (sqrt area) | n GT | AP baseline / replicate / P2 / 1600 | recall (AR) baseline / replicate / P2 / 1600 |
|---|---|---|---|
| <16 px | 380 | 0.013 / 0.004 / 0.005 / 0.015 | 0.040 / 0.038 / 0.038 / 0.033 |
| 16-24 px | 7,376 | 0.056 / 0.035 / 0.045 / 0.053 | 0.126 / 0.122 / 0.099 / 0.124 |
| 24-32 px | 14,154 | 0.098 / 0.112 / 0.094 / 0.105 | 0.205 / 0.237 / 0.198 / 0.254 |

Observations: recall of objects under 16 px stays at 3-4% for every run. P2 has the lowest recall at 16-24 px. imgsz 1600 has
the highest recall at 24-32 px and 32-96 px; P2 has the highest at >96 px (0.412). On val_fast, AP_small moves by up to ±0.02 between consecutive epochs of the same run
(`figures/learning_curve.png`, right). That is larger than most AP_S differences between runs.

## 7. Dense scenes (acceptance 2)

val_full mAP by targets per frame (`density.csv`; bins of 977 / 1,062 / 618 / 189 frames):

| run | 0-19 | 20-49 | 50-99 | >=100 |
|---|---|---|---|---|
| baseline (CH-09) | 0.046 | 0.142 | 0.184 | 0.284 |
| replicate | 0.052 | 0.165 | 0.184 | 0.296 |
| P2 | **0.106** | 0.167 | 0.177 | 0.267 |
| imgsz 1600 | 0.063 | **0.186** | **0.196** | **0.325** |

- imgsz 1600 is the best run in the three denser bins, by +0.01 to +0.03 over the replicate.
- P2 doubles the sparse-frame bin (0-19 targets) but is the lowest run on the densest bin.
- mAP rises with density for every run. The bins also differ in which clips and scene types they contain; that was not broken
  down here.
- maxDets 500 vs 100: the gain grows with density, from 0.000 (0-19) to 0.035-0.041 (>=100). The 500 cap matters most in dense
  frames, for every variant.

## 9. Speed and cost (acceptance: speed; hardware separated)

One RTX 5070 Laptop session, the shared benchmark (batch 1, FP32, 30 preloaded val_full frames, letterbox + NMS + rescale),
median of 3 interleaved rounds (`speed_same_session/summary.json`; round-to-round spread ≤ 3%):

| model | imgsz | FPS | latency ms | train wall s (RTX 5070) | peak train CUDA GB |
|---|---|---|---|---|---|
| baseline CH-09 checkpoint | 1344 | 73.3 | 13.6 | (2,003 on the RTX 3050) | 1.45 (3050) |
| replicate | 1344 | 71.6 | 14.0 | 1,568 | 1.45 |
| P2 | 1344 | 54.1 (−26%) | 18.5 | 1,841 | 2.42 |
| imgsz 1600 | 1600 | 48.3 (−34%) | 20.7 | 1,935* | 2.00 |
| RT-DETR-l (CH-11 baseline, same session) | 1344 | 13.6 | 73.4 | — | — |

\* Epoch 2 is slower than the other epochs in every RTX 5070 run: replicate 390 s, P2 435 s, against 217-300 s for the
other epochs. The cause was not identified. For `yolo_imgsz1600` it took 580 s, because it also overlapped the 2-epoch P2 smoke on
the same GPU, so about 2.5-3 min of its wall time is contention. Accuracy is unaffected, but the training-time comparison is
approximate.

Marko's RTX 3050 result for the CH-09 baseline (36.37 FPS, `results/yolo_baseline_marko_3050/speed.json`) is kept separately and
is **not** comparable with the RTX 5070 numbers. Absolute RT-DETR FPS differ between sessions: 10.6 in the CH-11 session,
13.6 here. Only within-session ratios are compared.

## 10. Failure cases (CH-07 rule, `failures.csv`, `results/<run>/figures/*.png`)

The same frames recur across runs. All four runs miss the same tiny person (15x36 px, `uav0000086_00000_v`), the best overlap
being IoU 0.24-0.36. Every run labels a van as a car (or a car as a van, for P2) at high IoU in `uav0000117_02622_v`. In the dense
frame `uav0000117_02622_v/0000301.jpg` (93 targets), all runs miss the same bicycle. The 1600 run predicts it as a tricycle at
IoU 0.67, while the others predict a person at IoU 0.29-0.35. The figures show individual frames. Their interpretation belongs to
the students.

## 11. Limitations

- One seed per configuration. A single replicate pair estimates the spread.
- Selection uses val_fast, a frame subset of val_full, so val_full is not an independent test set.
- The replicate's GPU differs from CH-09's.
- 1600 changes the input resolution and the compute.
- The P2 branch starts untrained and gets only the 6-epoch budget.
- Training wall time of `yolo_imgsz1600` is contaminated (section 9).
- Absolute FPS depend on the session.
